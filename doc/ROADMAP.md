# pi-app 发展路线图

> 最后更新：2026-08-14（访谈共识定稿，之后随进展滚动更新）
> 阅读要求：这份文档必须让没接触过 pi 的普通人都能看懂。如果你发现哪句话看不懂，那就是文档写得不好，请直接提出来改。

## pi-app 是什么

pi 是一个在终端（命令行）里运行的 AI 编程助手。**pi-app 是它的桌面版**：把聊天、代码改动、会话历史放进一个真正的窗口里，用鼠标和图形界面操作，不用记命令。

pi-app 的定位：**给普通桌面用户用的、友好又稳定的界面**。底层能力全部来自 pi 自己；pi-app 不重复发明功能，只负责把体验做好。想加什么能力，靠 pi 的插件体系，不靠改 pi-app 本身。

## 我们靠什么赢

市面上一堆 pi 的桌面外壳（文末有清单）。pi-app 靠三件事同时做对：

1. **稳定可靠**：每次改动都经过自动化测试把关，有明确的发版流程，修 bug 持续有节奏地进行，而不是三天打鱼两天晒网。
2. **完全兼容 pi 的插件**：你在终端版 pi 里装的任何插件，桌面版直接就能用，插件作者不用改任何东西。
3. **两边数据一致**：聊天记录、账号登录、设置文件，桌面版和终端版共用同一份。在终端聊到一半，打开桌面版能接着聊，不用导入导出。

## 做事的原则

1. **pi 保持简单，功能靠插件**：这是 pi 的设计哲学，桌面版完全遵守。我们讨论过"要不要在桌面版里预装一批官方插件"，结论是**不做**——想用什么插件，将来直接在界面里搜索、安装（见 G2）。
2. **先收拾旧的，再加新的**：新功能再炫，不如把现有的做扎实。路线图第一步是检查现有功能，不是加新东西。
3. **每次改动不破坏已有功能**：所有改动必须通过已有的自动检查，改坏了发不出去。
4. **自己的本事可以借给插件用，但自己不能变胖**：pi-app 已有的界面能力（展示、交互），可以做成通用组件给插件调用。比如：插件的配置文件不用手填 JSON 字段，而是由 pi-app 根据插件的说明自动生成下拉框、开关等表单。但前提是：组件必须通用（一个组件很多插件都能用），绝不为某一个插件写专属代码；核心永远保持精简、好维护。

## 怎么开发

- 借助 AI 辅助快速迭代开发；
- 小改进**每周发一个新版本**；大功能**一个用 1–3 个月**做出来；
- 每个功能开工前先写清楚"做到什么程度算完成"，完成就发版。

## 路线图（按先后顺序，前面没做完不着急做后面）

### 第 1 件事：检查现有功能，能简则简，该修就修（R0）

先把**已经有的功能**挨个检查一遍：哪个不好用、哪个几乎没人用、哪个有 bug。
- 不好用的，修好；
- 几乎没人用的，精简掉（删功能要写明理由，不能悄悄删）；
- 有 bug 的，修掉，并加测试防止以后再犯。

每周推进一个模块，比如：聊天时间线、会话树、输入框、文件面板、设置页。

优先处理历史更新记录里反复出现的老问题：启动慢、界面滚动卡、打开大仓库卡、设置页太复杂。

第一轮盘点已完成，见 `doc/R0-FEATURE-REVIEW.md`（功能清单 + 交叉评价 13 个热点 + 三档精简建议 + 待验证问题）。

**完成标准**：每个模块都有检查结论；每个改动都有理由；这段时间功能只减不增。

### 第 2 件事：把桌面体验打磨好（G1，每周发版）

持续小步改进，每周一个新版本：

- **更快**：启动快、打开大仓库快、翻很长的聊天记录不卡；
- **更稳**：出错时提示说人话，告诉用户发生了什么、该怎么办，而不是甩一串错误代码；
- **更好用**：中文输入法顺畅、长文本光标不乱跑、能用键盘翻历史消息。

**完成标准**：每项先测出"现在有多快/多稳"，再定一个明确目标；达到目标就写进更新日志，用户看得见。

### 第 3 件事：三个大功能（每个 1–3 个月）

**G2 插件管理界面**：两件事——"装"和"用"。

1. **搜索 / 安装 / 卸载**：在软件里直接搜索、安装、卸载插件。装了什么插件、从哪里装的、是谁的（软件自带的 / 你自己装的 / 项目专用的），一目了然；卸载要干净，不留残留文件。
2. **配置表单**：很多插件要改配置文件（一段 JSON），手填容易写错。pi-app 根据插件提供的字段说明，自动生成图形化表单——下拉框、开关、文本框——选完自动保存，格式错误当场提示，不用手动敲 JSON。实现要点：
   - 字段说明放在 pi-app 的适配配置里（沿用"自带的 / 你自己的 / 项目专用的"三层规则），**插件作者不用改一行代码**；
   - 保存时走 pi 官方的配置读写通道，保证和终端版设置不冲突；
   - 先做第一版（固定的字段说明）；"选项由插件动态提供"留到以后再说。

**G3 会话树增强**：会话树是 pi-app 的特色——聊天可以分叉、可以回退。这次增强三件事：
1. 把两个分支（或两个会话）的代码改动并排对比，看看哪里不一样；
2. 给分支起名字、加书签，重启后还在；
3. 树显示更宽、更好读，分支多了也不乱。

**G4 同时开多个会话 + 子任务面板**：
1. 几个会话同时开着，来回切换不会串状态；
2. 模型派生的子任务（子 agent）的进度和结果有专门面板展示，能点进去看它干了什么。

### 第 4 件事：移动端（C1）

参考 orca 的做法，做手机 / 平板版本。注意：移动端需要"远程执行"能力（模型跑在电脑上，手机连过去用），工作量不小，所以排在桌面大功能之后。前提是先把桌面端做扎实。

### 第 5 件事：让更多人知道 pi-app（G5，推广）

产品做好了，还要让人知道、装得上、上手快：

- 写一个**讲人话的对比页面**：pi-app 与社区里其它 pi 桌面软件、以及 Claude Code / Codex / DeepSeek 的区别，普通人一看就懂；
- 录演示视频；
- 写新手引导：从 Claude Code / Codex 转过来的用户，第一分钟该干什么；
- 中文、英文文档同步维护。

## 检查点（不设死期限，做到就算通过）

| 检查点 | 内容 | 大概时间 |
|--------|------|----------|
| M1 | 第 1 件事（R0）第一轮检查完成 + 第 2 件事（G1）首批"更快更稳"达标 | 2–4 周 |
| M2 第一段 | G2 的搜索 / 安装 / 卸载上线 | 1 个月内 |
| M2 第二段 | G2 的配置表单上线（图形化配置，不手填 JSON）；动态选项以后再说 | 随后 1–2 个月 |
| M3 | G3 会话树增强 + G4 多会话/子任务面板 | 1–3 个月 |

## 明确不做的事

1. **不做"每走一步都要用户点确认"的弹窗审批**。pi 的理念是信任用户、不打断干活；改错了可以在 Review 面板里事后检查。必要时只把危险操作标红提醒，不弹窗拦截。
2. **不预装官方插件包**（讨论过，否决了）。
3. **不做 MCP 官方插件**。MCP 是一种让 AI 连接外部工具的通用标准；有需要的留给社区插件，我们不官方维护。
4. **不改 pi 终端版**——那是另一个仓库（pi 本体），我们只依赖它，不动它。
5. **不在桌面版里另造一套内核**，也**不把数据分开存**——两边必须永远共用同一份数据。

结论：这个领域很碎片化，最高的也只有 199 个关注，说明**没人做出口碑**。pi-app 的机会在于"稳定 + 完全兼容 + 数据共享"三件事同时做对。需要留意的两类对手：用更轻量技术（Tauri）做的、主打启动快的；以及主打"复制 Claude Code 体验"的。我们的回应：前者靠第 2 件事（G1 把速度做上去），后者靠"我们不抄功能清单，我们做桌面窗口独有的东西"（时间线、会话树、多标签文件预览）。

### 三大主流终端 AI 编程助手（不是直接对手，作为对照）

- **Claude Code**：公认的"开箱即用"标杆——内置计划模式、待办清单、权限控制、费用显示。我们**不抄它的功能清单**：这些能力在 pi 里由插件提供，谁想要谁装；我们的桌面窗口（时间线、会话树、多标签文件预览）是它终端形态给不了的。
- **Codex**：卖点是界面快（用 Rust 重写）+ 沙盒隔离（在隔离环境里跑命令）。我们的桌面形态和它不冲突；把"更快"做好（G1）就是对它的回应。
- **DeepSeek**：中文市场的新对手。我们的中文文档 + 中文输入体验打磨，是中文用户直接能感受到的优势。
